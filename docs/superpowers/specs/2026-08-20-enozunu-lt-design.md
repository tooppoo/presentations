## 聴衆

skill / agent が何かは 1 枚で軽く揃えてから本題に入る。

## 構成方針

痛みの共感を重心に置く。
自分がコピペ運用で詰んだ経緯を時系列で語り、enozunu は解決策として後半に登場させる。

devcontainer は「不便だから使っている」のではなく「AI エージェントの事故を隔離したくて使っている」。
その隔離が効いているぶん、ホストのユーザーディレクトリも見えない。
この因果を 10 → 11 枚目の並びで見せる。

18 枚目で「宣言定義はコピーしている」と正直に言い、19 枚目でそれを次の課題として提示する。
残る手作業を自分で指摘してから将来構想に渡すことで、聴衆の「それコピペのままでは」という引っかかりを先回りする。

## 構成

### 第1部: 入口（1〜4）

1. カバー
2. 自己紹介（`pages/profile.md` を流用）
3. skill / agent とは。AI エージェントに作法を仕込むファイル群
4. skill を書いたら便利だった
   - 修正 → subagent レビュー → 修正 のループを skill 化。このスライド自体もそれで作っている
   - `git-kura` を使わせて、並行作業のコンフリクトをマージ前に自動検出

### 第2部: 痛み（5〜12）

5. 別のリポジトリでも同じ作法を使いたくなる
6. コピペした（`talk-step`）
7. その結果。コピーが増え、片方だけ古くなり、原本が分からなくなる
8. コピペの何が嫌なのか。バージョン管理はできる。欠けているのは同期の仕組み
9. ユーザーディレクトリに置けばいい（`talk-step`）
10. AI エージェントは devcontainer の中にいる。事故を隔離し、壊れても rebuild で取り返しがつくようにするため
11. 壁。その隔離が効いているぶん、ホストのユーザーディレクトリも見えない。マウントは隔離を薄くする
12. 図解。ホスト / コンテナの境界（`talk-diagram`）

10 の見出しは「なぜ devcontainer で動かしているか」ではなく事実の提示にする。
聴衆はその時点で、発表者が devcontainer を使っていることをまだ知らない。
理由は本文の `v-clicks` に置く。

### 第3部: 解決とこれから（13〜20）

13. 欲しかったもの。宣言だけ共有 / 更新はコマンド一発 / 生成物は捨てられる
14. enozunu（役小角）。宣言を各エージェントのネイティブパスへ materialize する CLI
15. `enozunu.kdl` 実例。このリポジトリの実物から `subagent-review-loop` の宣言を抜粋する
16. `enozunu summon` 一発で反映。lock ファイルで再現性
17. `.claude` / `.agents` は丸ごと gitignore。生成物になったので捨てて作り直せる
18. 変わったこと。定義は専用リポジトリで一元管理 / 同期の仕組みはそもそも不要 / 各プロジェクトへは宣言定義をコピーして再利用
19. これから。宣言定義のコピーすら要らなくしたい。リモート URL の宣言を extends（`tsconfig.json` のイメージ）
20. まとめ。skill / agent の管理をスムーズにするための道具として
